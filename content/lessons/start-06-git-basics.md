## Зачем нужен Git

Без Git история версий выглядит как `final_v2_ИСПРАВЛЕНО_final2.html`. Git заменяет этот фольклор: полная история изменений, откат к любой версии, параллельная работа без перезаписи друг друга. Система контроля версий (version control system) запоминает снимки проекта — коммиты — и позволяет свободно перемещаться между ними.

## Локальный и удалённый репозиторий

`git init` превращает обычную папку в репозиторий: внутри появляется скрытая папка `.git` — база данных всех версий. Пока всё локально: репозиторий живёт на вашей машине.

Удалённый репозиторий (remote) — копия на сервере: GitHub, GitLab или своём хостинге. Он нужен для совместной работы и резервной копии. Модель простая: **работаете вы всегда локально** — правите файлы и делаете коммиты, а `git push` отправляет новые коммиты на сервер, `git pull` — забирает чужие. До push сервер о ваших коммитах не знает ничего.

## Три области: папка, индекс, история

Файлы в Git живут в трёх областях:

1. **Рабочая папка** (working directory) — то, что вы видите в редакторе.
2. **Индекс** (staging area) — черновик будущего коммита: сюда складывают то, что в него войдёт.
3. **История** — зафиксированные снимки-коммиты.

`git add файл` кладёт текущее состояние файла в индекс. `git commit -m "сообщение"` превращает содержимое индекса в снимок и навсегда записывает его в историю. `git status` в любой момент показывает, что где: какие файлы изменились, что уже в индексе, что закоммичено.

Зачем `add` — отдельный шаг? Чтобы собирать коммит осмысленно. Вы правили десять файлов: три относятся к починке шапки сайта, семь — к экспериментам. Добавьте три, сделайте коммит «чинит выравнивание шапки» — история останется читаемой, а остальное подождёт в рабочей папке. Если коммитить всё разом, через месяц вы не отличите правку от черновика.

## Осмысленные коммиты

Флаг `-m` задаёт сообщение коммита. Хорошее сообщение объясняет причину изменения: «чинит пересчёт корзины при нулевом количестве» — а не «фикс» и не «изменил файлы». Историю читают другие разработчики и вы сами через полгода. `git log --oneline` показывает историю компактным списком, `git show <хеш>` — конкретный коммит.

## .gitignore

В корне проекта лежит файл `.gitignore` — список того, что Git не должен видеть: `.env` с паролями и ключами, `__pycache__/` и `venv/` — кеши и виртуальное окружение Python, `node_modules/` — зависимости фронтенда, `dist/` — результаты сборки. Правило: в репозиторий попадают код и тексты проекта; сгенерированные файлы и секреты — никогда.

## Ветки

Ветка (branch) — параллельная линия истории. Основная называется `main` (раньше — master). Команда `git switch -c fix-header` создаёт ветку и переключается на неё: коммиты копятся в ней, а `main` остаётся нетронутой. Когда правка готова, изменения сливают обратно: `git switch main`, затем `git merge fix-header`. Так экспериментируют, не боясь сломать рабочую версию, — и так же работают команды.

## Типичные ошибки

- Сделали `git add .` до того, как создали `.gitignore`, — и закоммитили `.env` с паролем от базы и гигабайты `node_modules`. Секрет, попавший в историю, нужно считать слитым навсегда: репозитории копируют форки и зеркала.
- Один огромный коммит «работаю» за целый день: историю невозможно ни прочитать, ни откатить.
- `git init` в подпапке существующего проекта — репозиторий внутри репозитория сбивает Git с толку.
- Закоммитили, но не запушили; сломался ноутбук — работа умерла вместе с ним. Удалённый репозиторий — и есть резервная копия, но только при регулярном push.
