## Зачем тесты и как их запускать

Тесты ловят регрессии: вы меняете код, а тесты сразу показывают, что сломалось. В Django они запускаются одной командой — отдельный сервер и база не нужны:

```bash
python manage.py test
```

Django создаёт временную тестовую базу, прогоняет тесты и удаляет её. Пишут тесты в `tests.py` приложения или в папке `tests/`.

## TestCase оборачивает тест в транзакцию

`django.test.TestCase` оборачивает каждый тестовый метод в транзакцию БД и откатывает её в конце. Поэтому данные не накапливаются между тестами, а сами тесты идут быстро.

```python
class PostModelTest(TestCase):
    def setUp(self):
        self.post = Post.objects.create(title="Привет", slug="hello")

    def test_str_returns_title(self):
        self.assertEqual(str(self.post), "Привет")
```

`TransactionTestCase` транзакцию не откатывает — реально коммитит и очищает таблицы. Он медленнее и нужен только тогда, когда вы тестируете само поведение транзакций (например, `atomic` или сигналы коммита).

## Client: HTTP без настоящего сервера

Внутри `TestCase` доступен `self.client` — он имитирует HTTP-запросы прямо в процессе, не поднимая сервер и не открывая сокетов.

```python
response = self.client.get(reverse("post_list"))
self.assertEqual(response.status_code, 200)
self.assertTemplateUsed(response, "posts/post_list.html")
self.assertContains(response, "Привет")
```

`reverse()` получает URL по имени маршрута, чтобы не хардкодить пути. `self.client.post(url, data)` отправляет форму; для аутентифицированных запросов есть `self.client.force_login(user)`.

## Данные: фикстуры и фабрики

Создавать объекты руками в каждом тесте утомительно. Есть три приёма:

- `setUpTestData(cls)` — создаёт общие данные один раз на класс, быстрее `setUp`.
- **Фикстуры** (fixtures) — готовые наборы данных в JSON/YAML: `fixtures = ["sample.json"]`.
- **Фабрики** (library `factory_boy`) — описывают, как собирать объект, и удобны для связанных моделей.

Фикстуры хороши для стабильных наборов, фабрики — когда каждый тест хочет слегка свои данные.

## Покрытие

Покрытие (coverage) показывает, какая доля строк кода выполняется тестами:

```bash
pip install coverage
coverage run manage.py test
coverage report
```

Цель не «100 % любой ценой», а уверенность, что покрыты важные ветки.

## Что обязательно тестировать

- **Бизнес-логику**: методы модели, расчёты, сервисный слой.
- **Формы и валидацию**: что неверные данные отклоняются, верные — принимаются.
- **Права доступа**: аноним не видит личное, автор не меняет чужое.
- **Критические пути**: оплата, регистрация, публикация.

## Типовая ошибка

Тест, который проверяет только `assertEqual(response.status_code, 200)`. Он пропустит пустую страницу, неверные данные и даже страницу, куда пользователя пускать не должны. Статус — одна проверка из многих: добавьте содержимое (`assertContains`), шаблон (`assertTemplateUsed`) и поведение для разных ролей. Второй промах — гонять тесты на рабочей базе: `TestCase` и так создаёт отдельную тестовую, трогать продакшн не нужно.
