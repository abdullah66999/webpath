## View: из запроса в ответ

View (представление) — функция или класс, которая принимает `request` и возвращает `response`. Чаще всего ответ — это HTML, собранный шаблоном с данными.

```python
def post_detail(request, slug):
    post = get_object_or_404(Post, slug=slug)
    return render(request, "posts/post_detail.html", {"post": post})
```

`render` склеивает шаблон и контекст. `get_object_or_404` возвращает объект или сразу отдаёт 404, если его нет, — не нужно писать `try/except`.

## urls.py: path() и конвертеры

URL связывается с view через `path()`. Конвертеры в строке извлекают часть адреса и передают её аргументом:

```python
urlpatterns = [
    path("posts/", PostListView.as_view(), name="post_list"),
    path("posts/<slug:slug>/", post_detail, name="post_detail"),
]
```

`<slug:slug>` поймает `/posts/hello-world/` и передаст `slug="hello-world"`. `name` нужен для `reverse` и тега `{% url %}` — так вы ссылаетесь на маршрут по имени, а не по строке. Пишите `path()`, а не `re_path()`: регулярки нужны редко, только для нетривиальных адресов.

## Функциональные и классовые view

Функция проста и наглядна. Класс удобен для типовых задач: `ListView`, `DetailView`, `CreateView` закрывают список, страницу объекта и форму в пару строк.

```python
class PostListView(ListView):
    model = Post
    paginate_by = 10
```

Оба подхода равноправны. Начинайте с функции, переходите на класс, когда логика становится шаблонной.

## Шаблоны и контекст

В шаблоне `{{ post.title }}` выводит значение, `{% for %}`, `{% if %}`, `{% extends %}` — теги логики. Данные приходят из контекста, который собирает view.

```html
{% for post in posts %}
  <h2>{{ post.title }}</h2>
{% empty %}
  <p>Постов пока нет.</p>
{% endfor %}
```

Наследование убирает дублирование: `base.html` хранит общий каркас, дочерний шаблон переопределяет `{% block content %}`.

```html
{% extends "base.html" %}
{% block content %}...{% endblock %}
```

## QuerySet ленивый

Это фундаментально: `filter()`, `all()`, `order_by()` не выполняют SQL — они строят описание запроса. В базу он уходит только при вычислении: итерация, срез, `list()`, `len()`, `bool()` или сериализация.

```python
qs = Post.objects.filter(published=True)   # запроса к базе ещё нет
qs = qs.order_by("-created_at")            # всё ещё нет
posts = list(qs)                           # вот теперь SQL выполнен
```

Благодаря ленивости queryset можно уточнять по частям и не дёргать базу зря. Но есть и ловушка: `if Post.objects.filter(...)` выполнит запрос, хотя вы хотели лишь собрать условие.

## Типовая ошибка

Логика в шаблоне. Шаблон должен показывать данные, а не считать их: `{% if post.comments.count > 0 %}` дёргает базу прямо из разметки, а фильтр `{% for %}` по не-`select_related` объектам порождает N+1. Подготовьте данные во view (или в методе модели) и передайте готовыми. Второй промах — забыть, что queryset ленивый, и вычислить его дважды: например, вызвать `len(qs)` в условии, а потом ещё раз проитерировать. Первое вычисление кэшируется, но только если вы переиспользуете одну и ту же переменную `qs`, а не пишете запрос заново.
