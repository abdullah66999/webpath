## REST — это соглашение о том, как разговаривать

REST (Representational State Transfer) не протокол и не стандарт, а набор договорённостей поверх HTTP. Соблюдать их выгодно: ваш API становится предсказуемым, и чужой клиент может угадать половину поведения, не читая документацию.

Центральное понятие — **ресурс** (resource). Всё, что имеет имя и состояние: задача, пользователь, заказ, комментарий. У ресурса есть URL и представление (representation) — то, в каком виде сервер его отдаёт, обычно JSON.

## URL — существительные, метод — глагол

Самая частая ошибка новичка — спрятать действие в путь:

```text
плохо                              хорошо
POST /api/createTask               POST   /api/tasks
GET  /api/getTaskById?id=5         GET    /api/tasks/5
POST /api/tasks/5/markAsDone       PATCH  /api/tasks/5
GET  /api/users/7/getBookmarks     GET    /api/users/7/bookmarks
DELETE /api/deleteAllTasks         DELETE /api/tasks
```

Правила, которые покрывают 90 % случаев:

- Только существительные во множественном числе: `/api/tasks`, а не `/api/task`.
- Иерархия отражает принадлежность: `/api/users/7/bookmarks` — закладки пользователя 7.
- Действие выражает метод HTTP: `GET` читает, `POST` создаёт, `PUT` заменяет, `PATCH` правит часть полей, `DELETE` удаляет.
- Вложенность не глубже двух уровней. `/api/users/7/bookmarks/3/comments/9` — уже перебор, лучше `/api/comments/9`.
- Фильтры, сортировка и пагинация живут в query-параметрах: `/api/tasks?done=false&order=-created&limit=20`.
- Слова через дефис в нижнем регистре, без подчёркиваний и CamelCase.

## PUT против PATCH

`PUT /api/tasks/5` с телом `{"done": true}` — это **полная замена** ресурса. Честный сервер запишет задачу, у которой нет заголовка. Если нужно поменять одно поле и не трогать остальные — это `PATCH`. Путаница между ними ломает клиентов молча: данные просто исчезают.

На практике многие API трактуют `PUT` как «обновить переданные поля». Это допустимо, но тогда поведение должно быть одинаковым во всех эндпоинтах и описанным в документации.

## Коды ответов — часть дизайна

Проектируя эндпоинт, вы сразу прописываете не только успех:

- `GET /api/tasks` → `200` со списком задач; если задач нет — пустой список, а не `404`.
- `GET /api/tasks/999` → `404`, потому что конкретной задачи нет.
- `POST /api/tasks` → `201` и заголовок `Location` с адресом созданной задачи.
- `POST` с пустым `title` → `400` или `422` с описанием, что именно не так.
- `DELETE /api/tasks/5` → `204` без тела; повторный `DELETE` → `404`.
- `POST /api/users` с уже занятым email → `409 Conflict`.

## Версионирование

Формат ответа однажды придётся поменять несовместимо. Заложите версию сразу: `/api/v1/tasks`. Старая версия живёт, пока последний клиент не переедет. Менять поведение `v1` задним числом — значит сломать чужой код без предупреждения.

## Типичная ошибка: 200 на всё

```python
@app.get("/api/tasks/<int:task_id>")
def get_task(task_id):
    task = TASKS.get(task_id)
    if task is None:
        return jsonify({"success": False, "message": "не найдено"})  # и статус 200
    return jsonify({"success": True, "data": task})
```

Клиент обязан распарсить тело, чтобы понять, что произошло. Мониторинг, прокси и кэш видят только `200` и считают, что всё хорошо. Правильно — вернуть `404`, а в теле оставить короткое описание ошибки.
