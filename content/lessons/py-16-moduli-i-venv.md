## Модуль — это просто файл

Каждый `.py`-файл — **модуль** (module): его код выполняется один раз при первом импорте, а имена из него становятся доступны через точку.

```python
import math                  # весь модуль, обращаемся math.pi, math.ceil
from math import ceil        # одно имя, обращаемся просто ceil
from math import pi as PI    # с сокращением имени
import numpy as np           # сокращают и целые модули (np — соглашение)
```

`from math import *` заманчиво, но плохо: имена из модуля смешиваются с вашими, и невозможно понять, откуда взялась функция. Импортируйте явно.

Python ищет модули по списку путей: сначала папка запускаемого скрипта, затем стандартная библиотека, затем установленные пакеты. Поэтому ваш `helpers.py`, лежащий рядом со скриптом, импортируется как `import helpers`. Два модуля, импортирующих друг друга, создают **циклический импорт** (circular import) — он падает или работает наполовину; лечится переносом общего кода в третий модуль.

## if __name__ == "__main__"

У каждого модуля есть встроенная переменная `__name__`. При запуске файла напрямую `python script.py` она равна `"__main__"`, а при импорте — имени модуля, например `"script"`. Отсюда защита, которую вы увидите в каждом втором проекте:

```python
def main():
    print("запускаем расчёт")

if __name__ == "__main__":
    main()
```

Смысл: тестовый или демонстрационный запуск выполняется **только** когда файл запустили как скрипт. При импорте модуля из другого файла ничего лишнего не произойдёт. Логика при этом живёт в функции `main()`, а не на верхнем уровне.

## Пакет — папка с модулями

**Пакет** (package) — директория с файлом `__init__.py` (может быть пустым) и модулями внутри:

```text
shop/                  # пакет
├── __init__.py
├── models.py
└── pricing.py
main.py                # скрипт рядом с пакетом
```

```python
from shop.pricing import apply_discount
import shop.models
```

Импорт от имени пакета — `shop.pricing`, через точку. Так проект раскладывают по файлам: модели отдельно, работа с ценами отдельно. Пакеты вкладываются друг в друга, и крупные проекты (Flask, Django) — это многоуровневые пакеты.

## pip: чужие пакеты

Стандартная библиотека покрывает многое, но за готовыми решениями ходят в PyPI — репозиторий пакетов Python. Устанавливает их **pip**:

```bash
pip install requests          # поставить пакет
pip uninstall requests        # удалить
pip show requests             # версия и зависимости
pip list                      # всё установленное
```

Имя пакета в pip и имя для импорта могут отличаться: `pip install Pillow` → `import PIL`, `pip install python-dateutil` → `import dateutil`. Это частая причина «поставил, а не импортируется».

## venv: своё окружение для каждого проекта

Если ставить всё в один глобальный Python, проекты начнут конфликтовать: одному нужен `Django 4`, другому `Django 5`. **Виртуальное окружение** (virtual environment) — отдельная папка со своей копией интерпретатора и своим набором пакетов:

```bash
python -m venv .venv               # создать окружение в папке .venv
source .venv/bin/activate          # активировать (macOS/Linux)
.venv\Scripts\activate             # активировать (Windows)
pip install requests               # пакет поставится внутрь .venv
deactivate                         # выйти
```

После активации в приглашении терминала появляется `(.venv)`, и `pip`/`python` работают с этим окружением. Правило: **один проект — одно окружение**, папку `.venv` добавляют в `.gitignore` — в репозиторий её не коммитят.

## requirements.txt: список зависимостей

Окружение не переносится на другую машину — переносится список пакетов:

```bash
pip freeze > requirements.txt      # зафиксировать текущие версии
pip install -r requirements.txt    # восстановить на другой машине
```

Файл выглядит как `requests==2.31.0` — по строке на пакет с точной версией. Без `-r` pip попытается установить пакет с именем «requirements.txt» и упадёт.

## Частые ошибки

- Забыли активировать venv — пакет ставится в глобальный Python, а в проекте не находится.
- `pip install requests` прошёл, а `import request` падает — опечатка в имени импорта.
- Зависимости не зафиксированы в `requirements.txt` — у коллеги проект не запускается.
- Демонстрационный код написан на верхнем уровне модуля без `if __name__ == "__main__"` — он выполняется при каждом импорте.
