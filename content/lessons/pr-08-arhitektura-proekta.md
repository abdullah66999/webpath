## Структура продакшн-проекта

Учебный скрипт в одном файле и боевой проект различаются структурой. Когда кода много, его раскладывают так, чтобы любую часть можно было найти, прочитать и протестировать отдельно.

```text
myapp/
  app/
    __init__.py        # фабрика приложения
    routes/            # HTTP: blueprints / контроллеры
    services/          # бизнес-логика
    repository/        # доступ к базе данных
    models.py          # модели SQLAlchemy
    config.py          # конфигурация из окружения
  tests/               # тесты pytest
  migrations/          # миграции Alembic
  requirements.txt
  .env.example         # ключи конфига без значений
  Dockerfile
  .github/workflows/ci.yml
```

## Слои: routes → services → repository

Продакшн-код делят на три слоя, каждый отвечает за своё:

- **routes / контроллеры** — принимают HTTP, валидируют ввод, вызывают сервис и возвращают ответ. Никакой бизнес-логики и SQL здесь нет.
- **services** — бизнес-логика: посчитать отчёт, применить правила. Сервис не знает ни про HTTP, ни про конкретную базу.
- **repository** — доступ к данным: SQL-запросы и работа с ORM.

Зачем: каждый слой тестируется изолированно, логику можно переиспользовать, а базу или способ доставки (веб, CLI, API) — поменять, не переписывая ядро. Смешанная в контроллерах логика быстро превращается в нечитаемый клубок.

## Конфигурация и 12-factor

**12-factor app** — набор принципов для приложений, которые живут в облаке. Ключевые для вас:

- **Конфигурация в окружении** — всё, что отличается между средами (`SECRET_KEY`, `DATABASE_URL`, `DEBUG`), хранится в переменных окружения, а не в коде.
- **Логи как поток событий** — приложение пишет логи в stdout, а куда их собрать, решает окружение.
- **Dev/prod parity** — среды разработки и продакшна держат максимально похожими, а деплой автоматизируют, чтобы расхождение не порождало баги.
- **Процессы без состояния** — состояние живёт в базе, а не в памяти процесса: любой воркер может обработать любой запрос.

## Дипломный проект: «Трекер расходов»

Соберите приложение, которое связывает всё пройденное: фронтенд, бэкенд на Flask или Django API, базу, тесты и деплой. Идея на выбор — трекер личных расходов.

**Что строим.** Веб-приложение: пользователь регистрируется, входит, добавляет доходы и расходы по категориям и видит отчёты.

**Обязательные фичи:**

- Регистрация и вход; пароли через bcrypt/PBKDF2, сессии или JWT.
- CRUD записей: сумма, категория, дата, комментарий.
- Категории (связь «записи — многие к одной категории»).
- Отчёт: суммы по категориям и по месяцам (агрегатные SQL-запросы).
- Фронтенд: форма добавления, список записей, простая диаграмма.
- Тесты pytest на логику и ключевые сценарии API.
- Деплой: публичный HTTPS-адрес, `DEBUG=False`, Postgres, CI с тестами.

**Опциональные фичи:** экспорт в CSV/JSON, бюджеты с предупреждением о превышении, поиск и фильтры, упаковка в Docker + docker-compose.

**Критерии готовности (Definition of Done):**

- Код на GitHub; README объясняет задачу, архитектуру и как запустить.
- CI зелёный: линтер и тесты проходят на каждый push.
- Приложение доступно по публичному HTTPS-адресу, база внешняя.
- Структура слоистая (routes/services/repository), секретов в репозитории нет.

**План на 4 недели:**

1. Схема базы и модели, каркас проекта, конфиг через окружение, первые тесты.
2. Аутентификация, CRUD записей и категорий, API.
3. Отчёты, фронтенд, экспорт (опционально).
4. Docker, CI/CD, деплой, README, полировка.

## Типичные ошибки

- Бизнес-логика и SQL прямо в контроллерах.
- Конфиг и секреты в коде вместо окружения.
- Проект без тестов и README — такой не показать работодателю.
- Взялись за все фичи сразу и не довели MVP до деплоя.
