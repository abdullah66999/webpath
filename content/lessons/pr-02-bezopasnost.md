## Безопасность — это не одна настройка

Безопасность нельзя «включить» в конце. Это набор решений, которые вы принимаете каждый день. **OWASP Top 10** — список самых частых уязвимостей веб-приложений; ниже — те из них, с которыми вы столкнётесь первыми, и жёсткие правила против них.

## Секреты живут только в переменных окружения

`SECRET_KEY`, пароли базы, токены API — это **секреты**. Их не бывает в коде и не бывает в репозитории. Только переменные окружения (environment variables).

```python
import os
SECRET_KEY = os.environ["SECRET_KEY"]   # не "supersecret123" в файле
```

Локально их удобно держать в файле `.env`, который добавлен в `.gitignore`. В репозиторий кладут `.env.example` — те же ключи, но без значений.

Если секрет **уже закоммичен** — удаление из файла не помогает. История Git помнит всё, а значит секрет считается скомпрометированным. Порядок действий: **сначала ротация** (выпустить новый ключ/пароль и отозвать старый), потом вычистить секрет из истории (`git filter-repo` или BFG). Просто удалить строку в новом коммите — недостаточно.

## SQL — только параметризованный

Никогда не склеивайте SQL из пользовательских данных. Это **SQL-инъекция (SQL injection)**:

```python
# УЯЗВИМО: вход подставляется прямо в строку
cursor.execute(f"SELECT * FROM users WHERE name = '{name}'")

# ПРАВИЛЬНО: значение передаётся отдельно от запроса
cursor.execute("SELECT * FROM users WHERE name = %s", (name,))
```

В первом варианте ввод `' OR '1'='1` ломает условие. Во втором драйвер сам экранирует значение. SQLAlchemy делает это по умолчанию — не пишите сырой SQL строкой.

## XSS: чужой HTML экранируется

**XSS (cross-site scripting)** — когда в страницу попадает чужой скрипт. Jinja2 экранирует вывод автоматически. Как только вы пишете `{{ comment | safe }}` или вставляете пользовательские данные через `innerHTML` в JavaScript, вы своими руками отключаете защиту. Данные от пользователя — никогда не «безопасный» HTML.

## CSRF-токен обязателен

Любая форма, меняющая состояние (POST/PUT/DELETE), обязана нести **CSRF-токен** — иначе чужой сайт отправит запрос от имени залогиненного пользователя. Во Flask это Flask-WTF (`{{ form.hidden_tag() }}`), в Django — `{% csrf_token %}`.

## DEBUG=False в проде

В боевом режиме `DEBUG=False`. При `DEBUG=True` страница ошибки показывает стектрейс, переменные окружения и куски кода — то есть отдаёт атакующему карту приложения.

## Зависимости устаревают и дырявятся

Уязвимости находят в чужих библиотеках. Прогоняйте `pip-audit` по зависимостям и включите Dependabot в репозитории — они подскажут, какую версию поднять.

## HTTPS везде и правильные заголовки

HTTPS обязателен, Let's Encrypt выдаёт сертификаты бесплатно. Плюс защитные заголовки ответа:

- `Content-Security-Policy` — ограничивает, откуда браузеру брать скрипты; главный барьер против XSS.
- `X-Content-Type-Options: nosniff` — запрещает браузеру угадывать тип содержимого.
- `Strict-Transport-Security` (HSTS) — велит браузеру ходить только по HTTPS.

## Пароли — только медленный хеш

Пароли хранят как хеш с солью через **bcrypt, argon2 или PBKDF2**. Никогда MD5 и SHA1: они быстрые, поэтому их перебирают миллиардами в секунду. Медленный хеш с уникальной солью делает перебор бессмысленным.

## Типичные ошибки

- `SECRET_KEY = "..."` захардкожен в `settings.py` и уехал в Git.
- `DEBUG=True` на боевом сервере.
- SQL собран f-строкой из данных формы.
- `| safe` или `innerHTML` на пользовательском вводе.
