## Данные, которые исчезают

Вы недавно собрали To-Do API: задачи живут в словаре Python, обработчики читают и пишут в него. Всё работает — до первого перезапуска сервера. Процесс завершился, словарь испарился из оперативной памяти, задачи пользователя пропали.

Дело не в Python. Данные в переменных живут ровно столько, сколько живёт процесс. Чтобы сохранить их, нужно записать на диск и уметь быстро находить обратно. Первая мысль — выгружать словарь в JSON-файл.

## Почему не JSON-файл

Для сотни записей файл работает: сохранили целиком, загрузили целиком. На десятках тысяч записей всё ломается одновременно:

- Чтобы найти одну задачу, приходится читать в память весь файл и перебирать его.
- Чтобы изменить одну строку, нужно перезаписать весь файл.
- Два одновременных запроса перезапишут данные друг друга — блокировок нет.
- «Дай все невыполненные задачи, отсортированные по дате» означает каждый раз писать перебор вручную.

База данных (database, БД) решает все четыре проблемы: хранит данные на диске, но позволяет запросом просить ровно то, что нужно, не загружая всё.

## Таблицы, строки, столбцы

Реляционная база данных организует данные в **таблицы** (table). Таблица — сетка из **столбцов** (column) и **строк** (row). У столбца есть имя и тип: `id` — целое число, `title` — строка, `done` — булево значение. Строка — одна запись, одна задача.

Таблицы связываются друг с другом. Вместо того чтобы дублировать имя клиента в каждом заказе, в таблице `orders` хранят `user_id` — ссылку на строку таблицы `users`. Это и есть **связь** (relation), от неё название модели. Каждая порция информации живёт ровно в одном месте.

## Ключи

Строки нужно уметь отличать друг от друга. **Первичный ключ** (primary key) — столбец, значение которого уникально для всей таблицы. Обычно это `id`, который СУБД присваивает сама. Столбец, который ссылается на первичный ключ другой таблицы, называют **внешним ключом** (foreign key). База сама следит за целостностью: не примет заказ, ссылающийся на несуществующего пользователя.

## SQL читается почти как язык

Запросы к базе пишут на **SQL** (Structured Query Language). Язык декларативный: вы описываете, *что* хотите получить, а *как* — решает СУБД.

```sql
SELECT title FROM tasks WHERE done = 0;
```

«Выбери title из таблицы tasks, где done равно нулю».

## Типовая ошибка

Искушение свалить всё в одну гигантскую таблицу, «чтобы не связывать». Тогда имя клиента копируется в каждый заказ, а переименование означает охоту за всеми копиями: пропустите одну — данные разъедутся. Правильный путь обратный: разбить на таблицы, связать ключами и хранить каждый факт один раз.
