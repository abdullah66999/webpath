## Что значит «работает везде»

Кроссбраузерность (cross-browser compatibility) — это не «выглядит пиксель в пиксель в шести браузерах». Это «сайт решает задачу пользователя в каждом браузере, который вы заявили как поддерживаемый». Тень у кнопки в Safari может отличаться от Chrome, и это нормально. Сломанная форма — нет.

Список поддерживаемых браузеров задают в начале проекта, а не в конце. Ориентир — доля рынка и аудитория: для внутреннего инструмента хватит двух последних версий Chrome, для магазина пенсионеров понадобится Safari на iOS и старый Android.

## caniuse и browserslist

Поддержку конкретного свойства проверяют на [caniuse.com](https://caniuse.com): вводите `gap`, получаете таблицу по браузерам и версиям, зелёные клетки — работает, жёлтые — с префиксом или частично.

Чтобы не повторять этот список в десяти местах, его записывают один раз в **browserslist**:

```json
"browserslist": [
  "> 0.5%",
  "last 2 versions",
  "Firefox ESR",
  "not dead"
]
```

Эту строку читают autoprefixer, Babel и PostCSS — все инструменты понимают, под какие браузеры работать. Запросы означают: версии с долей выше 0.5%, две последние версии каждого браузера, ветка Firefox с расширенной поддержкой, кроме официально заброшенных.

## Вендорные префиксы и autoprefixer

Раньше экспериментальные свойства писали с префиксами — `-webkit-`, `-moz-`, `-ms-`. Вручную расставлять их сегодня бессмысленно: это делает **autoprefixer**, плагин PostCSS. Вы пишете чистый CSS, он добавляет префиксы только там, где они нужны выбранным браузерам, и только те, которые действительно нужны.

В Vite его подключают так: `npm install --save-dev autoprefixer postcss` и файл `postcss.config.js` с плагином в списке.

## Определяйте возможность, а не браузер

Проверять строку User-Agent — плохая идея. Она врёт: Edge представляется как Chrome, Chrome — как Mozilla, а новый браузер, которого не было в момент написания кода, не определится вообще. Правильный подход — **определение возможностей** (feature detection):

```css
@supports (display: grid) {
  .gallery { display: grid; }
}
```

```js
if ('IntersectionObserver' in window) {
  observeImages();
} else {
  showAllImagesAtOnce();
}
```

Сначала пишем то, что работает везде, затем добавляем улучшение для тех, кто его поддерживает.

## Progressive enhancement

**Прогрессивное улучшение** (progressive enhancement) — стратегия «сначала рабочий минимум, потом слои». HTML работает без CSS и без JavaScript: текст читается, форма отправляется на сервер. CSS делает это красивым, JavaScript — удобным. Если скрипт не загрузился или браузер старый, пользователь всё равно выполнит задачу.

Противоположный подход, graceful degradation, — сначала сделать максимум, а потом дописывать костыли для отстающих. Он дороже и ломается в непредсказанных местах.

## Polyfill и fallback — не одно и то же

- **Полифил** (polyfill) — библиотека, которая добавляет браузеру отсутствующий стандартный API: `core-js` для методов массивов, `whatwg-fetch` для `fetch`. Ваш код при этом не меняется.
- **Фолбэк** (fallback) — другое поведение вместо недоступного: вместо плавной анимации появления — мгновенное, вместо `loading="lazy"` — обычные картинки.

Полифил стоит денег: он увеличивает размер бандла для всех пользователей, даже для тех, у кого API есть. Поэтому его подключают условно, отдельным бандлом с атрибутом `nomodule`, — современные браузеры такой скрипт проигнорируют.

## Типичные ошибки

- Тестировали только в Chrome на рабочем компьютере — на телефоне меню не нажимается.
- Префиксы расставлены вручную и частично: autoprefixer сделал бы это точно.
- Определяют браузер по User-Agent и отдают другую страницу.
- Полифил тащит в бандл 200 КБ ради одного метода, который есть у 97% посетителей.
- Забыли, что `@supports` проверяет синтаксис, а не реальную работоспособность свойства.
