## Зачем нужен CI/CD

Ручной прогон тестов перед каждым коммитом — это дисциплина, которой не хватает. **CI (continuous integration)** снимает задачу с человека: на каждый push и pull_request автоматически запускаются линтеры и тесты. Сломанный код не попадёт в основную ветку, потому что проверка зелёная — условие слияния. **CD (continuous delivery/deployment)** идёт дальше и автоматически выкатывает прошедший проверку код.

Ценность простая: обратная связь приходит за минуты, а не «когда вспомнили», и одна и та же проверка воспроизводится на каждой машине одинаково.

## Где живут workflow

**GitHub Actions** описывает автоматизацию в YAML-файлах внутри `.github/workflows/`. GitHub сам находит их и запускает по указанным событиям. Файл в репозитории — часть кода: его версионируют, ревьюят и правят как обычный исходник.

## Анатомия workflow

```yaml
name: CI

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"
          cache: "pip"
      - run: pip install -r requirements.txt
      - run: pytest -v
```

Ключевые поля:

- `on` — триггеры: на какие события реагировать (`push`, `pull_request`, можно ограничить ветки).
- `jobs` — задачи; у каждой `runs-on` (ОС раннера) и `steps`.
- `steps` — последовательность действий: `uses` подключает готовый экшен, `run` выполняет команду в шелле.
- `actions/checkout@v4` — клонирует репозиторий на раннер. `actions/setup-python@v5` — ставит нужную версию Python.

Версии `@v4` и `@v5` фиксируют мажорную версию экшена — так сборка не сломается от внезапного обновления.

## Кэш зависимостей

Установка пакетов каждый раз заново — главная трата времени в CI. `cache: "pip"` в `setup-python` сохраняет загруженные пакеты между запусками: если `requirements.txt` не изменился, pip берёт их из кэша, и прогон ускоряется в разы. Это оптимизация, а не обязательное требование.

## Линтеры и тесты

Проверка состоит из двух частей: **стиль и статический анализ** (ruff, flake8, mypy) ловят подозрительный код до запуска, **тесты** (pytest) проверяют поведение. Обе — шаги одного job:

```yaml
      - run: pip install -r requirements.txt ruff
      - run: ruff check .          # линтер
      - run: pytest -v             # тесты
```

Если любой шаг завершился ненулевым кодом, весь job красный.

## Автодеплой

Отдельный job выкатывает код, когда тесты прошли и событие — push в `main`:

```yaml
  deploy:
    needs: test
    if: github.ref == 'refs/heads/main' && github.event_name == 'push'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: ./deploy.sh
        env:
          DEPLOY_TOKEN: ${{ secrets.DEPLOY_TOKEN }}
```

`needs: test` не даст деплою стартовать до зелёных тестов. Секреты (`DEPLOY_TOKEN`) хранятся в настройках репозитория и подставляются через `${{ secrets.* }}` — в коде их нет.

## Типичные ошибки

- Workflow положили не в `.github/workflows/` — GitHub его не видит.
- Нет кэша — каждая сборка ставит зависимости с нуля и идёт минуты.
- Тесты есть, но не блокируют слияние: красный CI игнорируют и всё равно мержат.
- Секрет вписали прямо в YAML вместо `${{ secrets.* }}`.
