## Зачем писать тесты

Пока проект маленький, вы держите его в голове. Как только кода становится больше, любое изменение превращается в лотерею: поправили одну функцию — молча сломали другую, и узнаёте об этом от пользователя в проде. Автоматические тесты (tests) — это страховочная сетка. Набор проверок, который запускается одной командой и за секунды говорит, сломалось ли то, что вчера работало.

Главное правило, которое отличает профессионала от новичка: **тесты пишут до релиза, а не после**. Написать тесты «потом, когда будет время» — значит не написать их никогда.

## pytest: тест как обычная функция

В Python есть встроенный `unittest`, но в продакшне почти везде используют **pytest**. Причина простая: тест — это обычная функция, а проверка — обычный `assert`, без бойлерплейта.

pytest сам находит файлы `test_*.py` и функции `test_*` внутри них и запускает их.

```python
def total(items):
    return sum(i["price"] * i["qty"] for i in items)

def test_total_empty():
    assert total([]) == 0

def test_total_sums():
    assert total([{"price": 100, "qty": 2}]) == 200
```

Если `assert` не сошёлся, тест падает, и pytest показывает, какое именно выражение и с какими значениями провалилось.

## Фикстуры: подготовка контекста

**Фикстура** (fixture) — это не «глобальная переменная», а подготовка и разбор контекста для теста. Она создаётся заново перед каждым тестом, который её просит, и при необходимости корректно убирается после.

```python
import pytest

@pytest.fixture
def client():
    app.config["TESTING"] = True
    with app.test_client() as c:
        yield c          # всё, что после yield, выполнится после теста
```

Тест получает фикстуру просто как аргумент с тем же именем:

```python
def test_index(client):
    assert client.get("/").status_code == 200
```

Так каждый тест работает со свежим, изолированным состоянием и не зависит от соседей.

## Параметризация вместо копипасты

Если одна и та же проверка нужна на десяти наборах данных, не копируйте тест десять раз. Используйте `@pytest.mark.parametrize`:

```python
@pytest.mark.parametrize("qty,expected", [(1, 10), (0, 0), (3, 30)])
def test_line_total(qty, expected):
    assert 10 * qty == expected
```

pytest запустит функцию трижды — по одному прогону на каждый набор.

## Пирамида тестов

Тесты делятся на уровни, и их количество образует **пирамиду**:

- **Юнит-тесты** (unit) — проверяют одну функцию или класс. Их больше всего: они быстрые, дешёвые и точно указывают, что сломалось.
- **Интеграционные** (integration) — проверяют связку нескольких частей, например запрос в базу. Их меньше.
- **End-to-end** (E2E) — прогоняют сценарий целиком, как пользователь. Их единицы: они медленные и хрупкие.

Перевёрнутая пирамида (много E2E, мало юнитов) — антипаттерн: такие тесты долго идут и часто ломаются без реальной ошибки.

## Покрытие — ориентир, а не цель

**Coverage** показывает, какой процент строк кода выполнился при прогоне тестов. Полезно, чтобы найти места, куда тесты вообще не заглядывают. Но 100% покрытия **не гарантирует** отсутствие багов: тест может просто выполнить код без единого `assert`. Относитесь к покрытию как к подсказке, а не как к цели.

## Типичные ошибки

- Тест зависит от другого теста или от порядка запуска — по отдельности они падают.
- Тест проверяет всё сразу и падает по десяти причинам; хороший тест падает по одной.
- `assert True` ради галочки: покрытие растёт, пользы ноль.
- Тестируют только «счастливый путь», забывая про пустой ввод, ноль и ошибки.
